## Requerimientos no funcionales y límites

- **RNF-01:** se mantienen separados los registros `participation` (un `Set` de electores que votaron) y `votes` (opciones por papeleta y peso, sin identidad de elector). **Advertencia:** pesos individuales singulares pueden reidentificar por inferencia; falta diseño de privacidad para producción.
- **RNF-02:** todas las operaciones del dominio resuelven recursos dentro de `ctx.orgId` y de una identidad de la misma organización. No hay sistema real de login; cambiar contexto desde la demo **no** autentica.
- **RNF-03:** `results()` deniega resultados por opción hasta que el estado es CERRADO; `monitor()` solamente retorna el agregado de emitidos, pendientes y habilitados.
- **RF-03 / RF-27:** todavía no existe backend ni almacenamiento cifrado o transacciones de base de datos. El voto único e irreversibilidad están simulados dentro de la misma instancia de JavaScript.
- **RF-16:** el prototipo asigna el peso completo a cada selección cuando se permiten múltiples opciones; la especificación deja pendiente validar el algoritmo de agregación y la precisión para esas elecciones.
- **RF-15:** permitir mínimo 0/votar en blanco figura en el documento como decisión propuesta pendiente de validación con el cliente; el prototipo lo admite, sin incorporar voto nulo implícito.
- **Autenticación:** de acuerdo con el documento se excluye el registro/login real del prototipo inicial; se usan identidades precargadas.
